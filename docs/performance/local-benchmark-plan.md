# CityAI Hub 本机压测方案与候选配置

核对日期：2026-10-22。状态：方案与配置草案；未执行压测，无性能实测结果。

3200 TPS、P95 180ms、6500 QPS、P95 32ms、命中率 96% 均来自待验证的描述，作为目标而非已取得的成绩。配置不能保证达到这些数值。库存零超卖需限定测试场景、轮次与核对时点。

## 1. 环境与现有实现

- 已读取的本机硬件：Intel Core i9-14900HX，24 核、32 逻辑处理器，物理内存约 15.7 GiB。不能描述为独立服务器压测。
- 项目声明 Java 17 / Spring Boot 3.2.4。当前 PATH 的 java 指向 JDK 25，Maven 路径版本为 3.9.11；建议正式测试选择项目要求的 JDK 17，确认 `java -version`、`mvn -v` 使用一致版本并记录，不能将项目声明版本当作实际运行版本，也不能假定当前 JDK 25 已通过兼容性验证。
- 当前 PATH 未发现 JMeter/k6；未找到项目压测脚本或支持上述指标的原始报告。
- README 描述 Redis 运行于 WSL、部分服务运行于 Docker、本地 MySQL/RocketMQ；实际测试前需记录各服务版本、运行位置、CPU/内存限制及持久化设置，不能当作已经核验过的部署拓扑。
- 本机压测机与被测服务会竞争 CPU、内存、磁盘。后台任务、GC、WSL/Docker 内存压力都应记录。若发生明显换页、压测端 CPU 饱和或无法发出目标流量，则不能将结果当作服务端极限。

## 2. 测量口径

每轮保存配置快照、提交号及工作区差异、测试数据批次、原始 JTL、错误分类、主机资源、MQ 积压和最终数据核对结果。预热、爬坡、稳定阶段分别标记；延迟分位数从对应阶段的原始样本计算，不能平均多个 P95 得到总体 P95。

| 指标 | 正确统计口径 | 目标 |
|---|---|---|
| 全部请求吞吐 | 测量窗口内完成的 HTTP 请求数 / 秒；成功与拒绝分列 | 如实记录 |
| 秒杀受理 TPS | `success=true` 且返回有效订单 ID 的请求数 / 秒 | 候选目标 3200/s |
| HTTP P95 | 同一窗口全部秒杀请求耗时的第 95 百分位，另列受理成功子集 P95 | 候选目标 ≤180ms |
| 订单提交 TPS | 数据库已提交新增订单数 / 秒 | 单独实测，不用受理 TPS 替代 |
| 最终落单延迟 | 从请求开始/受理完成到事务提交的延迟，明确起点 | 需额外采集，当前无完整埋点 |
| 店铺有效 QPS | 店铺查询 `success=true` 且返回正确 ID 的请求数 / 秒 | 候选目标 6500/s |
| 店铺 HTTP P95 | 同一查询场景全部样本 P95，另列失败/成功子集 | 候选目标 ≤32ms |
| 店铺缓存命中率 | 店铺缓存查询中 value-hit 与 empty-hit 的统计，见第 5 节 | 候选目标 ≥96% |

峰值统一使用稳定阶段的 10 秒窗口，附全阶段平均吞吐、平均延迟、P95、P99、错误率，不挑单个极短尖峰。若吞吐、延迟或命中率来自不同场景，必须分别标注。

1000 并发线程/虚拟用户不等于 1000 个请求始终在途。若确实在无思考时间的稳态保持 1000 请求在途，3200 请求/s 对应平均响应时间约 312.5ms；P95 180ms 需要结合长尾、P99、超时解释，不能用 P95 代替平均响应时间套公式。

## 3. JMeter 的公共设置

- 使用非 GUI 模式运行，关闭“查看结果树”等逐请求展示，保存精简 JTL，测试后生成报告。
- HTTP Keep-Alive 开启；连接超时建议 2000ms、响应超时建议 5000ms；超时请求计入错误，不丢弃。
- 阶梯并发先 100、300、500，再到 1000。先做小流量验证 token、请求路径、JSON 断言和数据准备。
- 热点查询每档爬坡 30 秒、稳定测量 120 秒，候选最大稳定档再测 300 秒；每个关键场景至少 3 轮。不要在同一窗口混入秒杀测试。
- 秒杀按第 4 节的数据量另设时间，不使用 1000 个固定身份无限循环。
- 预热不纳入正式统计；登录/数据准备也不计入被测接口 TPS。
- 单接口只有一个 HTTP sampler 时，可用 Constant Throughput Timer 的“所有活动线程（共享）”模式限制总目标速率，单位为每分钟：3200/s 对应 192000/min，6500/s 对应 390000/min。这是发压目标，不是测试结果；保持最大线程数、思考时间、实际发出速率可见。达不到目标就如实记录。
- 推荐将网络错误、业务失败（限流/售罄/重复）、受理成功分别计数；性能场景业务失败不能因 HTTP 200 而算成功。正确性场景的预期拒绝也单独统计。

## 4. 秒杀：正确性与吞吐分开测试

### 4.1 正确性：库存 100，1000 个不同用户

1. 使用隔离测试数据库、Redis 和 MQ 资源，为本轮准备新优惠券。数据库和 Redis 初始库存都为 100，用户购买占用为空，布隆初始化完成。避免对开发数据做全量清空。
2. 提前准备 1000 个有效用户及 token，先验证少量身份。请求头使用 `authorization: <原始token>`，不加 `Bearer`。秒杀方法级限流按用户+券 ID 每分钟 1 次，因此每个用户每轮只请求一次。
3. 用 JMeter 同步定时器或等价屏障让 1000 个唯一用户并发发送一次 `POST /voucher-order/seckill/{voucherId}`。配置有界等待时间，避免线程因屏障参与者不足而永久挂起。
4. 按 JSON `success` 字段分类：`true` 是入口受理，`false` 是业务拒绝；HTTP 200 不代表受理成功。理论受理上限为 100，其他用户预期因 Lua 原子预扣返回库存不足；限流、鉴权、网络或系统错误均单列。
5. 在首笔受理后 15 分钟前核对，避免自动关单干扰；观察 RocketMQ 下单 Topic 消费进度/积压，并确认本轮每个订单均已落库、对应 `tb_seckill_order_dispatch.completed=1`，Redis 恢复队列及 `seckill:order:pending:<orderId>` 标记已清理。`completed=1` 只表示项目投递任务完成，不能替代 Broker 消费积压检查。存在消费故障或超出核对窗口时，本轮应标记为未收敛并按故障恢复场景核验。
6. 正常完成场景必须同时满足：受理数不超过 100；本轮每个受理订单 ID 最终可查且均为预期未支付状态；对应投递任务已完成且无本轮未完成任务/恢复副本/待处理标记；数据库库存和 Redis 库存均非负且相等；有效订单数+数据库剩余库存=100；同一用户+券没有重复有效订单。任一条件不满足都判定本轮失败。
7. 使用新活动、新数据重复 10 轮。只有 10 轮全部满足上述断言后，才能报告“本场景 10 轮未发现超卖”。

重复用户、重复 MQ 投递、消费失败、库存冷启动、支付/关单竞争仍需专项测试。入口 Redis Lua 原子限制同一活动中用户重复预占，订单消费者还通过 `tb_seckill_order_guard` 按用户+券持久化串行占用，可拦截不同订单 ID 的重复消息；旧库必须先完成占用表迁移，绕过订单消费者直接写订单表不受该保护。支付回调与超时关单通过同一条订单的状态条件更新竞争，关单和库存同步任务在同一数据库事务提交，Redis 回补由后台任务幂等重试；这些机制不等同于 MySQL 与 Redis 跨系统强一致，也不应表述成任意故障场景零超卖。

### 4.2 吞吐：库存与身份必须充足

- 对同一热点券测试成功受理 3200/s，30 秒至少需要 96000 个不同用户及有效 token；60 秒至少 192000 个。库存应覆盖计划请求量并留有余量，预热使用独立活动。秒杀脚本会在库存耗尽时原子拒绝请求且不回滚库存，低库存正确性场景不能用于测持续成功吞吐。
- 1000 并发执行线程可以从共享 CSV 中逐条领取不同身份；关闭循环读取，数据耗尽停止线程。身份不够时应缩短测试并标注为短时峰值，不能循环固定 token 冒充新用户。
- 1000 用户购买大量不同券也能构造足够组合，但它测的是多券场景，不能称为同一热点库存的单券结果。
- 本机先用较小数据和负载验证链路，确认内存和磁盘余量后再增加数据规模。不要为了达到 3200 而关闭鉴权、用户限流或真实 MQ 发送。
- 逐档增加请求速率，例如 500、1000、2000、3200/s；同一配置比较时使用同类型的新活动和数据。查询压测中的 5 分钟稳定窗口若用于成功秒杀，3200/s 对应至少 960000 个唯一用户-券组合，需要额外容量规划。
- 请求线程不写数据库 outbox；后台 worker 从 Redis 恢复队列批量落库并领取最多 500 条 outbox 任务投递 RocketMQ。15 分钟到期时间保存在投递表中，到期后 worker 发送普通关单消息并持久化重试失败。消费者写库和单券库存行锁仍可能成为瓶颈。必须记录 MQ 下单消费积压、已提交订单速率和积压消退时间，并把 HTTP 受理速率与数据库落单速率分开报告。
- 如果入口短时达到 3200/s，但积压持续增加，则只能写“入口短时受理峰值”，不能写“全链路稳定下单 3200 TPS”。

## 5. 店铺缓存：热点性能与命中率分开测试

### 5.1 热点查询性能

- 接口 `GET /shop/{id}`，直接访问 8083；默认使用匿名请求，项目允许该路径匿名访问。不附 token，避免混入登录 Hash 查询和续期；如果另测登录态版本，独立报告。
- 选择实际存在且已加入布隆过滤器的店铺，预热 10～100 家；如果当前数据不足，使用实际数量并记录，不虚报数据规模。
- 随机访问固定热点集合，验证 `success=true` 及响应店铺 ID。逐档增加并发和目标速率，最终观察 6500/s 与 P95≤32ms 是否能同时成立。
- 使用现有 30 分钟 TTL，短时间纯预热热点命中率可能接近 100%。不能为了匹配 96% 将这一结果改写成 96%。

### 5.2 混合访问命中率

- 另设热点与长尾场景，例如 95% 请求访问预热热点、5% 请求访问真实存在的长尾。提前固定 ID 分布、随机种子、数据规模、TTL、持续时长和并发。
- 热点访问比例不是命中率：长尾首次回源后也会被缓存；并发请求、失效、更新删除缓存都会改变实际结果。不要事先构造 96% 热点请求再称其为优化收益。
- 店铺缓存计数器现位于 `CacheClient` 与 `ShopServiceImpl` 的实际分支，按结果统计 `value_hit`、`empty_hit`、`miss`、`bloom_reject` 和 `error`，不按店铺 ID 建立高基数指标。单体及业务服务开放 Actuator metrics，可查询 `/actuator/metrics/cityai.shop.cache.requests`，用 `tag=result:<结果>` 分别读取计数；做负载测试时记录测试前后计数差值，避免把进程启动以来的累计值当成本轮命中率。
- 查询命中率定义：`(value-hit + empty-hit) / (value-hit + empty-hit + miss)`。同时报告正值命中率 `value-hit / 总缓存查询数`，避免空值缓存抬高正常店铺命中的含义。`bloom_reject` 是缓存 GET 未命中后、数据库回源前的独立结果；它不计入上述命中率分母。
- Redis `INFO stats` 的全局命中计数混有登录、布隆等访问，不能直接当店铺缓存命中率；布隆 1% 误判率也不等于缓存 99% 命中。
- 若热点性能与混合访问不是同一场景，报告应分为“热点 QPS/P95”与“混合访问命中率”；不能合并暗示在同一负载下同时取得三项结果。
- 逻辑过期已是店铺详情的实际运行路径。比较缓存策略时应覆盖逻辑过期窗口，并与其他策略使用相同流量；同时记录 `cityai.shop.cache.refresh.rejections`，以判断后台重建池是否过载。

## 6. 本机候选配置

同目录 `application-localbench.yaml` 是独立、可选择加载的候选参数，现有 `src/main/resources/application.yaml` 未改动。先测原配置基线，再测候选配置，并保留两份结果；调优时每次只改变一类参数。

| 参数 | 候选起点 | 理由与边界 |
|---|---|---|
| Tomcat 最大线程 | 200 | 先使用可控起点，不把 1000 用户直接映射成 1000 服务线程；若线程等待且 CPU/依赖有余量，再比较 300/400 |
| Tomcat 最小空闲线程 | 20 | 减少小规模线程创建抖动 |
| 最大连接数/accept-count | 2000 / 200 | 支持连接复用和一定排队；不是 TPS 保证，也不能靠加长队列改善延迟 |
| Hikari 最大/最小空闲 | 20 / 5 | 同机数据库从适中连接数开始；单库存行争用不会因加连接自动消失 |
| Hikari 等待连接超时 | 3000ms | 避免无限排队，连接超时应计入失败 |
| 后端 JVM | 建议 `-Xms512m -Xmx2g -XX:+UseG1GC` | 给本机其他服务留内存；保留实际 GC/内存记录 |
| JMeter JVM | 可先最大堆 1GiB | 1000 线程还有堆外/栈内存；发现发压端不足需调整或分机测试 |
| SQL 日志 | `NoLoggingImpl` | 关闭逐 SQL 标准输出；应用 WARN/ERROR 保留并单独统计 |
| 应用日志 | `com.hmdp=warn` | 避免每单 INFO 输出干扰；基线与调优结果须注明差异 |
| AI 索引初始化 | 关闭 | 本轮专测缓存/订单；这不等于所有 AI/Milvus 自动配置已关闭 |
| Redis | 基线和候选配置均使用已绑定的 Lettuce 池配置，测实际连接与延迟 | 普通 Lettuce 非事务命令还可复用共享连接，不能从“池只有10”推导最多10并发 |
| MQ | 记录当前配置与消费速率，不编造线程/队列数 | 线程数、队列数和持久化策略未测，不通过假设修改来承诺 TPS |
| TTL、布隆、限流、15分钟关单 | 保持当前业务规则 | 不用改变业务正确性来制造好看的结果 |

从项目根目录启动已构建的独立压测实例时，可使用以下示例。先切换到项目要求的 JDK 17 并确认 `java -version`，再准备隔离的测试数据库、Redis、MQ 地址及既有必要环境变量；当前项目不能只靠切换一个 profile 自动隔离所有服务。

```powershell
java -Xms512m -Xmx2g -XX:+UseG1GC -jar .\target\hm-dianping-0.0.1-SNAPSHOT.jar --spring.config.additional-location=file:./docs/performance/application-localbench.yaml
```
